Scope & limits

The audit reads the actual repository: all 33 files in drizzle/ plus the migration journal, every module under app/server/**, the Drizzle schema, routes, the listing wizard, payment modal, image uploader, admin shell, and auth pages, plus deploy config. tsc --noEmit passes. The test suite passes 8 of 8. eslint is referenced by package.json but is not installed.

The live database was not inspected. The Supabase tooling available in this session is bound to a different project (gyjepnqtzaupbwuvkyxu) than the one .env targets (gbnnerrcezlgeuohaume).

Unverified, and assumed only from source: whether every migration is applied, runtime RLS state, index existence, seeded RBAC rows (roles / permissions / role_permissions), storage bucket & policies, query plans, and the Supabase security / performance advisors. A full production build was not run. Treat every Database finding as “from migration and schema source.”

Architecture snapshot

Stack: Vite + TanStack Start / Router, React 19 RC, Drizzle ORM over postgres-js, Supabase (Auth + Storage + Postgres), TanStack Query, Radix + Tailwind, Zod, Firebase Admin for FCM.

Data access: the web app connects as the Postgres owner role and bypasses RLS entirely. RLS exists only to guard a separate React Native app that shares the same database through the anon / authenticated keys.

Server functions: ~114 createServerFn endpoints with no global auth or RBAC middleware — each function must self-check, and several do not.

Effective product today: a classifieds site — listings, tiered listing fees, seller packages, admin moderation, RBAC, and WaafiPay for listing fees. The transactional marketplace from the PRD (buyer checkout, orders, payouts, escrow, disputes, delivery confirmation) is schema plus admin stubs only.

Security

20/100

2 critical · 3 high · 6 medium · 1 low

SEC-1

Password reset returns the reset token in the HTTP response → full account takeover

Critical
Location
app/server/password-reset.functions.ts:18-41, routes/auth/forgot-password.tsx:41-45, routes/auth/reset-password.tsx:37-67
Problem
requestPasswordReset returns { token, email } to the caller; the client then navigates to /auth/reset-password?token=… and resetPasswordByToken calls supabase.auth.admin.updateUserById. No email is ever sent — there is no mail integration in the repo. Anyone who knows an email address can reset that account’s password, including admins. The token also travels in a URL query string, and unknown emails return 404 "Email not found" (enumeration).
Fix
Never return the token. Deliver it by email only; store a hash, single-use, short TTL. Return a generic 200 regardless of whether the address exists. Move the token out of the URL. Rate-limit per IP and per email.
SEC-2

Hardcoded admin credentials in the documented seed script

Critical
Location
scripts/seed-admin.ts:6-7 (admin@celis.so / CelisAdmin123!), documented in docs/operations/runbook.md as pnpm db:seed-admin
Problem
The only documented way to bootstrap a super-admin creates a well-known email and password committed to the repo and prints them. Run against production, the platform ships with a public super-admin login.
Fix
Require ADMIN_EMAIL / ADMIN_PASSWORD env vars (fail if absent) or generate a random password printed once; or use an invite flow. Rotate immediately anywhere this has run.
SEC-3

Unauthenticated signed storage upload URLs

High
Location
app/server/storage.functions.ts:11-15, storage.server.ts:26-49
Problem
getListingImageUploadUrl does no auth and no ownership check — only shape validation. Any anonymous caller can obtain a Supabase createSignedUploadUrl for path {sellerId}/… in a public bucket (the function even creates the bucket if missing). Open write primitive: arbitrary file hosting, storage-cost abuse, content served from your project. fileType is accepted but ignored.
Fix
Require a session; force sellerId = currentUser.id; assert seller role; provision the bucket at deploy, not in the request; enforce content type and size on the signed URL.
SEC-4

Broken access control — client-supplied sellerId / listingId trusted

High
Location
app/server/listings.functions.ts:73-108 (createListing), :41-46 (submitShopListing), :37-39 (fetchSellerListingEligibility); listings.server.ts:205-234
Problem
createListing calls requireSeller(data.sellerId) (only checks the row exists) then insertDraftListing(data.sellerId, …) — it never checks data.sellerId === currentUser.id. A user can create listings owned by any other user id. submitShopListing takes an arbitrary listingId + sellerId and submitListingForReview has no ownership check. fetchSellerListingEligibility discloses any seller’s package state.
Fix
Derive sellerId from the session server-side; never accept it from the client. Add listing.sellerId === user.id to every listing mutation. Make requireSeller actually assert the seller role.
SEC-5

No rate limiting or brute-force protection on auth; no email verification

High
Location
app/server/auth.functions.ts (signIn, signUp), password-reset.functions.ts
Problem
No rate limiting, lockout, or CAPTCHA on sign-in, sign-up, or reset. signUp uses the service role with email_confirm: true — no email verification, so anyone can register unlimited accounts against any address and act as that identity. Compounds SEC-1.
Fix
Per-IP / per-identifier rate limiting at the edge; require email confirmation for customer signups; exponential backoff / lockout on failed sign-in.
SEC-6

Stored XSS via JSON-LD injection on the listing detail page

Medium
Location
app/routes/listings.$id.tsx:701-719
Problem
<script type="application/ld+json" dangerouslySetInnerHTML={{ __html: JSON.stringify({ name: listing.title, … }) }} />. JSON.stringify does not escape < or /, so a title containing </script><img src=x onerror=…> breaks out. Seller-controlled content; a seller can view their own unapproved listing, and a moderator views it pre-approval.
Fix
Escape < > & and U+2028 / U+2029 in the serialized JSON, or emit JSON-LD through a vetted head-meta path instead of dangerouslySetInnerHTML.
SEC-7

Listing detail server function leaks seller phone & non-public listings

Medium
Location
app/server/listings.functions.ts:112-116 → getListingById (listings.server.ts:126-174)
Problem
The route loader gates viewing to status === "active" || isOwner, but fetchListingById itself has no status or ownership check. A direct call returns full detail — including sellerPhone — for draft / pending / rejected / expired listings of other users, to any caller.
Fix
Enforce the same visibility rule inside getListingById; strip sellerPhone unless the listing is active or the caller is the owner / an authorized officer.
SEC-8

CSV formula injection in admin exports

Medium
Location
app/lib/csv.ts:8-14; consumers in admin.server.ts (ledger, failed-payments, new-users, new-listings exports) and routes/admin/reports.tsx
Problem
escape() handles quotes / commas / newlines but not leading = + - @ \t \r. Exported cells hold user-controlled data (emails, names, business names, references); opened in Excel / Sheets, =cmd|… payloads execute.
Fix
Prefix any cell starting with = + - @ \t \r with ', or export .xlsx with text-typed cells.
SEC-10

Audit log never records IP or request context

Medium
Location
app/db/schema/audit-logs.ts:16 (ipAddress column) vs app/server/audit.server.ts:36-45 (never set)
Problem
audit_logs.ip_address is always NULL. insertAuditLog re-derives the actor from the session but many call sites also stuff actorId into metadata — inconsistent. No user-agent or request id. Weaker than AGENTS.md’s “reconstructable” requirement for moderation / financial actions.
Fix
Capture IP + user-agent + request id from request context in insertAuditLog; stop double-storing actorId; consider an append-only / no-update policy on audit_logs.
SEC-11

SECURITY DEFINER RPCs with a mutable search_path

Medium
Location
drizzle/0022_*.sql, 0023_*.sql, 0024_*.sql (save_listing_with_fields, validate_listing_fields, update_listing_status, delete_listing, save_listing_images) use SET search_path TO public; only 0032 uses the hardened SET search_path = ''
Problem
SECURITY DEFINER with search_path pointed at a schema untrusted roles can write to is a privilege-escalation vector the Supabase linter flags. save_listing_with_fields also catches WHEN OTHERS and returns raw SQLERRM to the client.
Fix
SET search_path = '' and fully schema-qualify every object in all definer functions; return a generic error and log detail server-side.
SEC-12

Secrets & environment hygiene

Medium
Location
.env, app/lib/fcm.ts:9-17, scripts/process-notification-jobs.ts
Problem
.env (correctly gitignored) holds live-looking service-role key, DB password, and encryption key on the working machine. FIREBASE_SERVICE_ACCOUNT points to C:\Users\munii\Downloads\…json — absent in any deploy, so push notifications silently no-op in prod. NODE_ENV=development in .env. Key rotation for PAYMENT_CREDENTIALS_ENCRYPTION_KEY is one sentence with no runbook.
Fix
Secrets manager for deploys; ship Firebase creds as inline JSON; write a real key-rotation runbook; confirm .env never entered git history.
SEC-9

Open-redirect potential on post-auth navigation

Low
Location
routes/auth/sign-in.tsx:44, routes/sell.tsx:26, routes/dashboard.tsx:61
Problem
navigate({ to: redirect || "/dashboard" }) with redirect an unvalidated query value, not constrained to begin with a single /.

Validate redirect matches ^/(?!/) before use; otherwise fall back to /dashboard.

DB-1

Two conflicting identity models in one database

High
Location
app/db/schema/users.ts:22-25; drizzle/0000_small_ezekiel.sql:115 (CREATE TABLE "auth.users"), :325; vs 0025_chat_messaging.sql:13-14, 0028_notification_jobs.sql:13 (REFERENCES auth.users(id))
Problem
Web tables (users, profiles, listings, orders, payouts) FK to a mirror table literally named "auth.users" in the public schema, populated by app code. Mobile tables (conversations, messages, notification_jobs, listing_feedback, seller_reviews) FK to the real auth.users. An auth user created outside the web sign-in path has no mirror row and breaks web FKs; deleting from real auth.users does not cascade to the mirror; the two drift.
Fix
Reference auth.users directly via pgSchema("auth"); create the profiles row from an on_auth_user_created trigger; migrate the mirror away and backfill.
DB-2

Cascade deletes on financial / transactional tables

High
Location
orders.ts:22-27 (buyerId/sellerId → cascade), payouts.ts:22, payments.ts:26,56, plus reviews/listingReviews
Problem
Deleting a user (or the upstream mirror row) cascades away orders, payouts, wallet payments and reviews — destroying the financial ledger and audit trail. Collides with orders.listingId → restrict (a partially-failing cascade chain). A future “delete my account” (public info page already exists) would erase records that must be retained.
Fix
ON DELETE RESTRICT (or SET NULL with retained snapshots) for all money-bearing tables; implement account deletion as anonymisation.
DB-3

Migration journal desynced; duplicate numbers; schema drift

High
Location
drizzle/meta/_journal.json (last entry 0031, skips 0019–0028); files 0018_happy_blob.sql + 0018_mobile_rls.sql, two 0026; app/db/schema/index.ts has no model for conversations, messages, listing_feedback, seller_reviews, notification_jobs
Problem
The journal does not track migrations 0019–0028 (hand-written SQL applied out of band). Two files share 0018, two share 0026. drizzle-kit migrate would not apply the untracked files and generate/push fights the hand-written state. At least 5 live tables have no Drizzle model.
Fix
Reconcile the journal (absorb or re-baseline), renumber duplicates, add models for every live table, pick one migration tool, add a drift check to CI, add a migration step to deploy.
DB-4

Dead / ineffective indexes; no real search index

Medium
Location
app/db/schema/listings.ts:53,87-90 (search_vector text column never written; btree index on it), :52,90 (btree index on the metadata jsonb column)
Problem
search_vector is never populated; its btree index is useless. searchListings uses title/description ILIKE '%term%' (leading wildcard, seq scan) and metadata ->> key = value; a btree on jsonb does not serve ->> queries. Marketplace search is a sequential scan.
Fix
Real tsvector column + trigger + GIN, or pg_trgm GIN on title/description. Replace the metadata btree with GIN (jsonb_path_ops) or per-key expression indexes. Drop search_vector if unused.
DB-5

Late, partial RLS; primary app bypasses it

Medium
Location
drizzle/0000_small_ezekiel.sql (no RLS); first RLS in 0018_mobile_rls.sql, more in 0019, 0022, 0025–0028, 0032
Problem
RLS was retrofitted only for the mobile app and only on a subset of tables. The web app connects as owner and bypasses all of it, so RLS correctness is untested by the primary app. 0032 removed public reads from profiles/users and added get_public_marketplace_profiles, but the live deny-by-default state cannot be confirmed here.
Fix
Run the Supabase security advisor on the real project to zero; add RLS allow/deny tests (anon JWT) for every policy.
DB-6

Idempotency keys persisted inside listings.metadata

Medium
Location
drizzle/0022_*.sql:292-315, 0023_*.sql:327-351 (metadata->>'_idempotency_key' full scan, then jsonb_set to store it permanently)
Problem
Every create does an unindexed scan over all listings’ metadata; the key is then stored on the row forever (bloat, and it leaks into any metadata read / metadata_schema sync).
Fix
Dedicated listing_idempotency(key pk, listing_id, created_at) table with TTL cleanup; keep it out of user-visible metadata.
DB-7

Data-type & modelling nits

Low
Location
listings.ts:49-50 (locationLat/Lng as integer), :51 (images text[] of full URLs), categories.ts (no is_active)
Problem
Integer lat/lng loses all sub-degree precision (≈111 km). Storing full URLs (not storage paths) makes bucket migration / cleanup hard; no storage cleanup on listing delete (orphaned objects). No category soft-delete.
Fix
numeric(9,6) or PostGIS geography(Point); store paths and derive URLs; add is_active/archived_at to categories; delete storage objects on hard delete.

BE-1

Buyer order lifecycle and payout lifecycle are unimplemented

High
Location
app/server/orders.server.ts — createOrder is called only from createAdminOrder; completeOrder ends with // TODO: trigger seller payout…; payouts is never inserted anywhere in app/; there is no /checkout route.
Problem
Listing detail offers “Show contact / Request call back / WhatsApp” only. No buyer checkout, order creation, payout creation, commission capture, or delivery / dispute handling — despite full schema and a documented order state machine. Admin Orders & Payouts screens act on rows that can only be created by hand.
Fix
Decide v1 scope. If P2P transactions are in scope this is a major build (checkout, order state machine, payout initiation + provider, commission settlement, disputes). If not, hide the order / payout admin surfaces and unreachable schema and document the classifieds-only model.
BE-2

No WaafiPay callback endpoint or reconciliation worker

High
Location
app/server/payments.server.ts:33-190, waafi.server.ts, db/schema/payments.ts (callbackPayload, callbackReceivedAt, status pending_reconciliation)
Problem
Payment status is decided only from the synchronous API_PURCHASE response. On timeout the row is left pending_reconciliation and the listing stays draft — but there is no webhook route and no background job to poll / reconcile. A seller can be debited while the listing never activates, recoverable only by a human.
Fix
Authenticated Waafi callback route that verifies the provider signature and transitions payment + listing atomically; a scheduled reconciliation job for stale processing / pending_reconciliation rows.
BE-3

Inconsistent auth / error handling across server functions

Medium
Location
throughout app/server/*.functions.ts — bare throw new Error("Unauthorized") vs CelisError (app/lib/errors.ts, used only in *.server.ts); clients string-match messages
Problem
No consistent HTTP status mapping; CelisError.status never reaches the client; the UI branches on English strings. fetchCurrentUserPermissions returns [] on no-user while others throw. The shared phoneSchema is not reused in the profile-update path.
Fix
A thin createServerFn wrapper requiring auth / permission and serialising CelisError → { code, message, status }, used everywhere; client branches on code. Reuse phoneSchema in every phone path.
BE-5

Notification worker is not HA / crash-safe

Medium
Location
scripts/process-notification-jobs.ts:135-167
Problem
SELECT … WHERE status='pending' … LIMIT 20 then UPDATE … IN (ids) is a race — two workers claim the same jobs. A crash mid-batch leaves jobs stuck in processing forever (no reclaim). No retry / backoff. Invalid-token cleanup does update … eq('fcm_token', token), nulling the token for every profile sharing that value.
Fix
Claim with UPDATE … WHERE id IN (SELECT id … FOR UPDATE SKIP LOCKED) RETURNING *; add attempts, next_attempt_at, and a stale-processing reclaim; clear tokens by id.
BE-4

Large files and triplicated config defaults

Low
Location
admin.server.ts (1,949 lines), listings.server.ts (835), routes/admin/settings.tsx (1,051), admin/categories.tsx (963); defaults defined in admin.server.ts CONFIG_DEFAULTS, config.server.ts DEFAULTS, and lib/pricing.ts DEFAULT_LISTING_TIERS
Problem
AGENTS.md flags these sizes as unacceptable for new work; the triplicated fee / commission defaults will diverge.
Fix
Split per AGENTS.md (shell / query / mutation / table / dialog); one source of truth for platform-config defaults.

Working well: clean *.server / *.functions split, Zod on inputs, permission checks on the admin surface, transactions on the sensitive multi-writes (role perms, gateway save, category delete), audit logging, encrypted gateway credentials, server-side pricing, payment idempotency + reconciliation states, financial snapshotting at order creation.

PERF-1

Marketplace search cannot scale

High
Location
app/server/listings.server.ts:408-483
Problem
title/description ILIKE '%q%' (leading wildcard, seq scan), metadata ->> key = value with no usable index, then a second full query for the total count with the same joins. Every search is O(all active listings) twice.
Fix
FTS or pg_trgm (see DB-4); count(*) OVER() or an approximate count; cache category counts and price range.
PERF-2

In-memory pagination of the financial ledger

Medium
Location
admin.server.ts:1459-1563 (getAdminLedgerRows loads all matching wallet_payments + payouts, concatenates, sorts and .slice()s in JS); exports hard-code limit: 10_000
Problem
Unbounded memory and DB transfer as volume grows; violates AGENTS.md “admin tables must paginate on the server.”
Fix
Push pagination / sort into SQL (a UNION ALL view or two keyset-paginated queries merged); stream CSV exports.
PERF-3

Public pages: serial multi-fetch, no HTTP caching

Medium

Combine per-page reads into one server function; short s-maxage / stale-while-revalidate on public GETs; memoise current user + permissions per request.

Remediation plan

Ordered from ship-blockers to cleanup. Phases are a real sequence — Phase 0 gates any deployment; later phases can overlap once it clears. References point at the finding IDs above.

PHASE 0

Critical blockers — before any deployment

~1 week
